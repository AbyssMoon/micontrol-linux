# Интерфейс прошивки

Справочник по WMI-интерфейсу `MiInterface` ноутбуков Xiaomi. Источник — разбор
ACPI-таблиц **REDMI Book Pro 14 2025** (SKU TM2411, BIOS RMAAR4B0P0505, SSDT
`XMCC1806`, метод `WMAA`) и проверка вызовами на этом ноутбуке. На других моделях
значения могут отличаться — сверяйтесь с таблицами своей машины
(см. [DEVELOPMENT.md](DEVELOPMENT.md#отладка-на-ноутбуке)).

Обозначения: ✅ — проверено вызовом на железе, 📄 — только по коду ACPI.

## Устройство

| | |
|---|---|
| ACPI-устройство | `\_SB.PC00.WMID` (`PNP0C14`) |
| Метод | `WMAA(instance, method_id = 1, buffer)` |
| WMI GUID методов | `B60BFB48-3E5B-49E4-A0E9-8CFFE1B3434B` |
| WMI GUID событий | `46C93E13-EE9B-4262-8488-563BCA757FEF` (`Notify(WMID, 0x20)`) |
| Хранилище | регистры EC `\_SB.PC00.LPCB.Q_EC.*` |

## Формат вызова

Вход — буфер 32 байта, `WMAA` читает его словами:

| Байты | Поле ASL | Смысл |
|---|---|---|
| 0–1 | `FUN1` | `00 FA` — чтение, `00 FB` — запись |
| 2–3 | `FUN2` | `00 CMD` — функция |
| 4–5 | `FUN3` | `ARG 00` — подфункция или значение |
| 6–9 | `FUN4` | `ARG2 00 00 00` — значение |

Ответ — буфер 32 байта `RETS`:

| Байты | Поле | Смысл |
|---|---|---|
| 0–1 | `SGER` | `00 80` — выполнено, `00 E0` — функция не поддерживается, `00 00` — ветка не выставила статус |
| 2–3 | `FUTR` | номер функции |
| 4–5 | `FRD0` | значение (режим) или эхо подфункции |
| 6–9 | `FRD1` | значение |

**Прошивка не проверяет значения.** Запись неизвестного значения в известную функцию
часто проходит со статусом `80` и ничего не делает, поэтому после записи значение надо
перечитывать (так делает `Device`).

Через `acpi_call`: `\_SB.PC00.WMID.WMAA 0x0 0x1 {0x00 0xfa 0x00 0x08 0x00 …}`; ответ
читается из `/proc/acpi/call` **одним `read()` с буфером ≥ 4 КиБ** — на меньший буфер
модуль возвращает 0 байт.

## Функции

### 0x08 — режим производительности

| Значение | Режим | Чтение | Запись | Регистры EC |
|---|---|---|---|---|
| `02` | тихий | ✅ | ✅ | `QFAN = 2` |
| `03` | турбо | ✅ | ✅ | `QFAN = 3` |
| `04` | максимум | ✅ | ✅ | `QFAN = 4` |
| `09` | авто | ✅ | ✅ | `QFAN = 9` |
| `0A` | ? | 📄 | 📄 | `QFAN = 0x0A` |
| `05`, `06` | ? | — | 📄 | `SMMD = 5/6`, `SMMT = 0`, вызов `NTDP` |
| `07`, `08` | ? | — | 📄 | `SMMT = 7/8`, `SMMD = 0`, вызов `NTDP` |
| `01` | баланс (старые модели) | — | ✅ игнорируется | ничего, но статус `80` |

- Чтение: `FRD0 = FUNR(0x16)`; возвращаются только 2, 3, 4, 9, 0x0A, иначе 0.
- Запись 2–4, 9, 0x0A сбрасывает `SMMD`/`SMMT` и шлёт событие `0x16`.
- Режим уходит в Intel DTT как `ODVP1` (см. ниже) — от него зависят лимиты мощности.

### 0x0A — микрофон и прочее

| ARG | Чтение | Запись (ARG2) | Регистр EC |
|---|---|---|---|
| `05` микрофон | ✅ `FRD1`: 1 — включён, 0 — заглушён | ✅ 1 — включить, иначе заглушить; пауза 150 мс, событие `0x21` | `MIUT` (1 = mute, индикатор на клавише) |
| `07` ? | 📄 `FRD1` 1/2/3 по `WMIT` = 0x11/0x22/0x33 | 📄 `WMIT = 1/2/3`, статус не выставляется | `WMIT` |
| `08` ? | — | 📄 `AILM = 0/1`, статус не выставляется | `AILM` |
| `09` ? | — | 📄 `LBLM = 0/1`, статус не выставляется | `LBLM` |

`FRD0` в ответе — эхо `ARG`. Назначение `WMIT`, `AILM`, `LBLM` неизвестно.

### 0x10 — батарея

| ARG | Чтение | Запись (ARG2) |
|---|---|---|
| `01` здоровье | ✅ `FRD1 = SOH1`, % | — |
| `02` лимит заряда | ✅ см. таблицу | ✅ см. таблицу |
| `03` блок питания | ✅ `FRD1`: 0 — `ADPW ≥ 100`, 1 — меньше (слабый адаптер?); от батареи читается 1 | — |
| прочие | ✅ статус `00 00`, данные 0 | — |

Лимит заряда — бит 0 регистра `LONL` (вкл/выкл) и порог `HBDA` в процентах:

| ARG2 | Порог | `HBDA` |
|---|---|---|
| `00` | без ограничения (бит `LONL` сброшен) | 100 |
| `04` | 90% | 0x5A |
| `01` | 80% | 0x50 |
| `05` | 70% | 0x46 |
| `06` | 60% | 0x3C |
| `07` | 50% | 0x32 |
| `08` | 40% | 0x28 |

Все значения проверены ✅, в том числе остановка заряда на пороге от сети. Ниже
порога EC сразу включает заряд, выше — держит «Not charging». Сразу после записи
статус батареи несколько секунд может быть «Not charging».

## События WMI

`QV20(type, id)` → `Notify(WMID, 0x20)`; `_WED` отдаёт `{type, id, value, …}`. В Linux
их получает драйвер `redmi-wmi` (клавиши → input-события).

Fn+K режим не меняет: EC шлёт только событие `0x28`, а переключать режим должна
программа (на Windows — Xiaomi). `redmi-wmi` это событие пропускает, поэтому круг
режимов делает `micontrold`. Ядро передаёт WMI-уведомление в netlink (`acpi_event`:
`wmi PNP0C14:00 0x20`) без данных, и демон читает номер события из поля `EVFN`
(`\_SB.PC00.WMID.EVFN`), которое `QV20` заполняет перед `Notify` ✅.

| id | Источник | value |
|---|---|---|
| `0x16` | смена режима (запись `WMAA` или EC, `_Q24`) | новый режим: 2, 3, 4, 9, 0x0A, 7, 8 |
| `0x21` | микрофон | 0/1 по `MIUT` |
| `0x05` | подсветка клавиатуры | 0, 5, 0x0A, 0x80 |
| `0x07` | Fn Lock | состояние |
| `0x09` | Caps Lock | состояние |
| `0x22` | `WMIT` | 1/2/3 |
| `0x28` | Fn+K (`_Q28`) ✅ | 1 |
| `0x11`–`0x15`, `0x17`, `0x1B`, `0x23`–`0x27` | горячие клавиши | 1 или 0 |

## Мощность CPU и Intel DTT

Режим из EC попадает в переменную DTT `ODVP1`
(`/sys/devices/platform/INTC1042:00/odvp1`, читается без root) ✅:

| Режим | тихий | турбо | максимум | авто |
|---|---|---|---|---|
| `ODVP1` | 2 | 1 | 4 | 0 |

`thermald --adaptive` (Fedora запускает его так по умолчанию) берёт таблицы Xiaomi из
`data_vault` (GDDV, сжат LZMA со смещения 148): политики `1_ac_crazy` … `8_dc_silence`,
`9_lid_close`, `11_ac_ddr_prot`, `ac/dc_smart_1/2`, условия — по `ODVP`. PL1, который он
выставляет ✅:

| Режим | от сети | от батареи |
|---|---|---|
| тихий | 35–45 Вт | 45 Вт |
| авто | 65 Вт | 65 Вт |
| турбо | 80 Вт | 65 Вт |
| максимум | 90 Вт | 65 Вт |

Но `thermald` пишет только в MMIO-домен RAPL (`intel-rapl-mmio:0`). В MSR-домене
(`intel-rapl:0`) BIOS держит **PL1 = 28 Вт**, а процессор соблюдает меньший из двух —
поэтому без синхронизации режимы почти не влияют на производительность. PL2 = 115 Вт.
При нагреве `thermald` снижает PL1 в MMIO (видели 90 → 80 Вт); синхронизация демона
следует за ним. От батареи потребление CPU упирается примерно в 36 Вт независимо от PL1
(причина не выяснена). Замеры — в `scripts/measure-modes.sh`.

## Драйвер ядра `bitland-mifs-wmi`

В свежих ядрах (на Fedora с ядром 7.2 — точно) есть драйвер для того же GUID, написанный для ноутбуков Bitland. На
TM2411 он грузится, но:

| Функция драйвера | Номер | На TM2411 |
|---|---|---|
| `platform_profile` | 0x08 | ожидает 0–3 вместо 2/3/4/9 → чтение даёт `EINVAL`; запись `balanced` (0) ничего не делает, `low-power` (2) включает тихий режим, `performance` отказывает из-за 0x13 |
| GPU mode | 0x09 | `E0` |
| скорость вентиляторов (hwmon) | 0x0D | `E0` → показывает 0 |
| RGB-подсветка, яркость | 0x10–0x12 | `E0` (0x10 — это батарея) |
| тип питания | 0x13 | `E0` |
| температура CPU | 0x16 | `E0` → показывает 0 |

Статус ответа драйвер не проверяет. Вывод: правильнее научить этот драйвер Xiaomi
(квирк по DMI), чем держать `acpi_call`.

## Открытые вопросы

- Что такое режим `0x0A` и режимы 5–8 (`SMMD`/`SMMT`)? Возможно, «умные» подрежимы
  (`smart_1/2` в таблицах DTT).
- Назначение `WMIT`, `AILM`, `LBLM` (`0x0A`/7–9).
- Забывает ли EC лимит заряда после сна или смены питания? Регистры `LONL`/`HBDA`
  живут в EC; демон на всякий случай применяет лимит заново (как оригинальный MIControl).
- Откуда потолок ~36 Вт CPU от батареи (psys, ток батареи?).
- Отличаются ли значения на других моделях 2024–2025 (Xiaomi Book, RedmiBook 16 и т. п.).
